# 纯空行冲突不再要求人工审批

方案最初基于 `feat/original-mr-status` 的 `29de7b1`。经确认，现于 `fix/blank-conflicts-without-approval` 实现，基于 `9acf179`，包含待审批私信通知。线上已有任务仍不自动修改。

## 目标

纯空行冲突仍由 Coco 解决并纳入结果校验，但不创建待确认 Discussion，不计入人工审批总数，不阻塞任务完成。记录和冲突 ID 保留，不能只在页面隐藏这些块，也不能伪装成人工已批准。

以任务 24 为例：仍保留 C0001～C0005，C0002～C0004 标记为“纯空行冲突，无需人工审批”；新任务只为 #1、#5 创建审批 Discussion，进度显示“人工审批 0/2，另有 3 块无需人工审批”。保留原编号，不把 #5 改成 #2。

## 判定规则

判定由 Conciliator 根据冻结的原始冲突输入执行，不让 Coco 决定是否免审批。

一个冲突块只有在 source 和 target 两侧都不含空格、制表符、CR、LF 之外的字符时，才属于纯空行冲突。允许一侧零行、另一侧有空行；两侧都是零行也归入此类。缺失数据不能当成空字符串来豁免。

| 两侧内容 | 是否免人工审批 |
|---|---|
| 一行空行 / 零行 | 是 |
| 多行空行 / 一行空行 | 是 |
| 只有空格或制表符的行 / 空行 | 是 |
| 代码 / 空内容 | 否，这是可能的删除冲突 |
| 注释 / 空内容 | 否 |
| 代码相同，但缩进或行尾空格不同 | 否 |
| 包含其他 Unicode 空白或不可见字符 | 否，首版不扩大规则 |

这里处理的是内容全为空白的冲突片段，不做整个文件忽略空白后的比较，也不启用 Git 全局忽略空白选项。

## 先修正空行信息丢失

当前解析器先 `splitlines(keepends=False)`，再用 `"\n".join(...)` 组装内容，使一行空行和零行都变成 `""`。在分类前修复这一点：保留每侧的原始行结束符，保证零行是 `""`，一行 LF 空行是 `"\n"`，空格、制表符和 CRLF 不被抹掉。

标记识别使用移除行结束符后的行，内容收集保留原文。同步检查 manifest、结果原文比较、报告和重解锁定校验，避免新增尾部换行造成误报。对已有持久化结果不能用有损的空字符串反推出原始空行数量。

报告用明确文字展示空白侧，例如“无内容”“1 行空行”“仅含空白字符，共 2 行”，不继续输出看起来相同的空代码框。真实代码仍原样展示。

## 审批状态与存储

增加 `ApprovalStatus.NOT_REQUIRED`，含义为“纯空行冲突，无需人工审批”。

- 每块仍保存 `conflict_blocks` 和关联 `approvals` 记录。
- 在保存新任务冲突清单的同一个事务内，纯空行块创建为 `NOT_REQUIRED`，其他块创建为 `PENDING`。
- `reviewer_email` 和 `reviewed_at` 留空，不生成 `BLOCK_APPROVED` 事件。
- 记录分类事件及原因，包括任务 ID、冲突 ID、每侧行数和免审批原因。重复准备任务时沿用已持久化分类，并校验冻结清单一致，不能重复创建记录或改变 ID。
- `NOT_REQUIRED` 不允许通过 approve、reject、approve all 或重解重置成 `PENDING`。

现有 `approvals.status` 是 `VARCHAR(16)`，`NOT_REQUIRED` 可以直接保存，不需要数据库 DDL。更新应用枚举、模型说明和查询条件即可。

## Coco 仍需解决全部冲突

首次 manifest 继续包含全部冲突 ID，并明确标记哪些是纯空行块。输出仍要求逐块覆盖，不能因为免审批而漏掉结果。

纯空行块采用固定策略：保留 source 侧原始空白，不借机修改相邻代码。Prompt 明确这一规则；这类块不要求按空行寻找业务作者，可按免审批规则返回空作者，服务端同步调整作者校验，不能把修复后保留的 `"\n"` 误当成有业务代码的非空侧。

免审批不等于免结果校验：

- 继续验证冻结 SHA、resolver HEAD、提交关系、结果 ID 完整性和冲突标记清除。
- 对纯空行块，结果必须仍为纯空白并符合保留 source 的策略，结合最终提交原文回读验证，不能仅相信 Coco 的文字说明。
- 自动处理块的定位/原文核对失败不能只记 warning 后豁免，应进入现有的一次修复流程；仍失败则任务失败。
- 若自动块处没有可用于行内评论的现存行，不因缺少 Discussion 锚点失败。对整份文件最终为空的情况，允许该自动块使用 `0/0` 表示无锚点，并在已确认分类及实际空文件的前提下校验；普通人工审批块继续要求正整数行号。涉及文件重命名、文件删除等既有不支持场景，不在本次放开。

## 发布、展示和审批完成

发布前先分出人工审批块和 `NOT_REQUIRED` 块。

- 只为人工审批块创建、回读和保存 Discussion，仅提醒这些块的作者。
- MR 描述、飞书报告和 resolve MR 的 `/resolve status` 明确分开“人工审批进度”与“无需人工审批的纯空行块”。免审批块可以保留简短说明，但不显示待勾选框，不显示 `unknown` 作者待确认。
- 单块 approve/reject、approve all、剩余数量、全部批准判断、MR 描述刷新、状态回复、指标和通知都使用同一套计数规则。
- `total_manual = PENDING + APPROVED + REJECTED`；`NOT_REQUIRED` 独立计数。缺失审批记录或未知状态不能被当作免审批。
- 完成事务核对全部冲突块都有合法审批记录，并确认每块为 `APPROVED` 或 `NOT_REQUIRED`。不能简单用内连接后的记录数相等来忽略缺失记录。
- 保留任务 version/CAS、active_key 释放和通知 outbox 的原子性，不允许取消与完成互相覆盖。

### 全部冲突都是纯空行

仍正常执行 Coco、验证提交、生成报告和创建 resolve MR。确认这些步骤成功后，自动完成审批流程，不进入无限等待人工评论的状态。

复用现有终态 `ALL_APPROVED`，事件注明 `completion_reason=NO_MANUAL_APPROVAL_REQUIRED`，人工批准数为 0，并记录免审批块数。对外显示“纯空行冲突已处理，无需人工审批”，不能写成“已有 N 人批准”或“MR 已合并”。原 MR 状态回复和完成通知同步处理这一文案。

完成操作放在仓储事务中，允许从发布完成的 `MR_CREATED` 进入 `ALL_APPROVED`，只在全部块为 `NOT_REQUIRED`、MR 已持久化且发布验证完成时使用。增加对应状态机转换，不先写入等待审批再依赖用户评论推动。重复执行只允许一次完成及一次通知。Worker 对已经完成发布、尚未完成该事务的全免审批任务补做收尾，避免进程在两个步骤之间退出后卡住。

不会自动合并 MR；最终合并仍由仓库和用户决定。

## 重解与自动修复

`/resolve retry` 仍只重解 `REJECTED` 的人工审批块。`NOT_REQUIRED` 块进入锁定集合，保持之前的解决结果，不在后续轮次补建 Discussion，也不重置审批状态。

同 Session 的校验自动修复保留服务端分类。Coco 不能通过改结果、漏掉 ID 或返回空字符串，把普通冲突改成免审批块。

## 已有任务

首版自动分类仅作用于新解析、尚未发布的任务；不在服务启动时批量修改线上已有审批。

任务 24 若要一并处理，使用定向修复流程：从 `conflict_files_snapshot` 重新解析并按 ID、文件和原始位置核对 C0002～C0004；检查当前解决提交以及任务/审批版本；只把仍为 `PENDING` 的对应记录改成 `NOT_REQUIRED`，保留审计记录，刷新 MR 计数与报告。已存在的 Discussion 不删除，另行明确标记无需审批，避免页面仍要求用户确认。已有人工批准、拒绝或后续重解时，不覆盖这些操作。

这涉及数据库和已发布评论的更新，实施时先读取最新状态并列出具体目标；本轮方案不执行这些写入。即使旧任务不补处理，新任务也应满足本方案全部行为。

## 验证与上线

回归测试覆盖零行、一行/多行空行、空格/制表符、CRLF、单侧代码删除、仅代码缩进差异，以及空白信息不丢失。

用任务 24 的冻结输入作为回归样例：5 个块保持原 ID，只有 C0001/C0005 创建审批 Discussion，进度从 0/2 到 2/2 后完成；其他 3 个块始终为 `NOT_REQUIRED`。

另测全部纯空行、结果混入非空白代码、位置核对失败、空文件、approve all、人工 reject 后 retry、并发取消、重复发布和完成前进程退出。真实仓储测试应证明免审批块不会阻塞完成，也不会使缺失审批记录被漏检。

部署无数据库迁移。需完成所有实例更新后再发起验证任务，避免旧版本 Worker 读取新审批状态。线上分别验证“代码与空行混合冲突”和“全部空行冲突”，核对 MR 评论、审批计数、数据库状态、trace 和完成通知。

## 实现说明

含免审批块的文件使用冻结快照重建：普通块填入本轮结果（重解时锁定块沿用已验证结果），纯空行块填入 source 原文，其余上下文保持不变。将重建内容与最终提交文件逐字比较，并从上下文计算自动块位置；这也用于保护重解中的空行块。Coco 的普通代码片段允许省略末尾行结束符，空行块则必须保留精确原文。

全免审批任务沿用 `ALL_APPROVED` 终态和完成事务，完成通知在现有 outbox 中使用 `NO_MANUAL_APPROVAL_REQUIRED` 类型以选择专用文案；首次待审批通知不会入队。已验证发布信息与 `MR_CREATED` 同事务写入，启动恢复和定期轮询都能补做完成事务。

自动化回归覆盖任务 24 的五块结构（其中 C0002～C0004 为单空行对零行），还覆盖原文及行号篡改、空文件、重解后位置平移、缺失审批记录、重复分类、全空行收尾、取消并发和发布中断恢复。测试中外部请求使用模拟响应；上线后的真实 MR 和飞书通知仍需在新版本完成发布后验证。
