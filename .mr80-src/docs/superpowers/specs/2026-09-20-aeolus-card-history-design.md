# aeolus 编码助手卡片状态与交互历史设计

## 背景与目标

现有 AI 节点卡片使用前端 Mock 串联输入校验、Coding、结果确认和反馈重试。此次改动保持 Mock 架构不变，完成三项调整：

1. 输入校验和每轮 Coding 都至少展示 10 秒处理状态。
2. 修正节点名称、成功提示和代码链接的颜色，提高阅读性。
3. 在卡片底部展示当前卡片会话内的逐轮 Coding 交互历史。

本次不接入真实后端，不持久化历史，也不改变 AI 节点属性或平台配置。

## 成功标准

- 节点触发后，输入校验状态持续 10 秒，再进入 Coding。
- 每次 Coding 状态持续 10 秒，再展示待确认结果。
- 用户每次提交有效反馈后，当前轮被完整保留，并新增下一轮 Coding 记录。
- 用户确认后，最新一轮标记为已完成。
- 历史按轮次展示状态、反馈和代码链接；最新轮默认展开，旧轮默认折叠且可展开。
- 页面刷新后历史清空，重新开始一次卡片会话。
- 卡片在窄屏下保持单列且内容可读。

## 范围与约束

- 仅修改 `aeolus-larkoffice` 中 aeolus AI 节点卡片及其单元测试。
- 继续使用现有 React 本地状态和 Mock 需求文档、Mock 代码链接。
- 不新增依赖，不新增网络请求，不修改持久化数据格式。
- 输入校验重试不计入 Coding 轮次。

## 交互流程

### 初次执行

1. 卡片以“输入校验”状态打开并等待 10 秒。
2. 校验失败时展示补充需求文档的提示和“重新校验”按钮；此时没有 Coding 历史。
3. 校验通过后创建第 1 轮记录，状态为“Coding 中”。
4. Coding 等待 10 秒后，第 1 轮进入“待确认”，展示代码链接、确认按钮和反馈输入框。

### 反馈并重新 Coding

1. 只有非空白反馈才能提交。
2. 提交后，当前轮状态更新为“已反馈”，并保存本轮反馈内容和代码链接。
3. 紧接着创建下一轮记录，状态为“Coding 中”，等待 10 秒。
4. 新一轮完成后进入“待确认”。该流程可以重复多次，所有已完成交互轮次都保留在当前会话中。

### 确认完成

用户点击“确认完成”后，当前轮状态更新为“已完成”，卡片主状态也进入“已完成”。代码链接继续可用，不再显示反馈操作。

### 失败与重试

- 输入校验失败沿用现有校验失败页面；重新校验不会创建 Coding 轮次。
- 异常导致的输入校验错误提供重试，并重新执行输入校验。
- 异常导致的 Coding 错误将当前轮标记为“处理失败”，提供重试按钮。
- Coding 重试复用失败的当前轮，不新增轮次，避免一次技术重试被误认为一次用户交互。
- 组件卸载或新操作覆盖旧操作时，旧异步结果不得回写状态。

## 状态与数据模型

卡片顶层阶段继续使用现有阶段：

- `validating`
- `validation_failed`
- `coding`
- `review`
- `completed`
- `error`

新增本地 `rounds` 数组保存 Coding 轮次。每轮包含：

```ts
type CodingRound = {
  id: number;
  status: 'coding' | 'review' | 'feedback' | 'completed' | 'error';
  feedback: string;
  codeUrl: string;
};
```

规则如下：

- 轮次 ID 从 1 递增，仅在用户反馈触发新 Coding 时增加。
- 当前轮为数组最后一项。
- Coding 完成时更新当前轮的 `codeUrl` 和状态，不创建额外记录。
- 反馈内容写入被反馈的轮次，新轮次的反馈为空。
- 展开/折叠属于纯 UI 状态，不写入轮次业务数据。
- 所有状态仅存在于当前 React 组件生命周期内。

轮次更新逻辑放在可独立测试的纯函数中，组件负责异步等待、渲染和调用这些函数。10 秒延迟常量与纯逻辑一同导出，避免组件和测试各自维护不同数值。

## 卡片布局与视觉

### 主卡片

- 白色背景，标题使用高对比深色 `#1F2329`。
- “AI 节点”使用紫色标签：文字 `#5B3CC4`，背景 `#F3F0FF`。
- 顶部状态标签继续按阶段区分蓝、紫、橙、绿。
- “代码已生成”成功提示使用深绿文字 `#176B3A`、浅绿背景 `#EAF8F0` 和边框 `#A9D9BD`。
- 代码链接使用深蓝 `#1456F0`，同时保留清晰边框和悬停/聚焦反馈。
- 不依赖浅色文字表达关键信息，确保节点名称、成功状态和操作链接在白底上清晰可读。

### 交互历史

- 历史位于当前操作区下方，以纵向时间线展示。
- 每项显示“第 N 轮”、状态标签、反馈摘要和代码链接。
- 最新一轮默认展开，展示完整状态和可用内容。
- 较早轮次默认折叠，点击标题可展开；折叠时仍能看到轮次和状态。
- 状态颜色语义：处理中为蓝色、待确认为紫色、已反馈为橙色、已完成为绿色、失败为红色。
- 在窄屏下使用单列布局，按钮和历史内容不横向溢出。

## 测试策略

在现有 `tests/workflow.test.cjs` 中以纯函数单元测试覆盖：

- 处理延迟为 10,000 毫秒。
- 首轮 Coding 记录的创建和完成。
- 有效反馈会结束当前轮并创建下一轮。
- 空白反馈不会创建新轮次。
- 连续三次反馈后，轮次顺序、反馈内容、状态和代码链接均被保留。
- 确认操作只完成最新一轮。
- Coding 失败及重试复用当前轮。
- 原有 READY 标记校验和顶层状态转换继续通过。

完成实现后执行：

```bash
npm test
lpm build
```

`npm test` 验证状态和历史纯逻辑，`lpm build` 验证卡片 TypeScript、样式和打包集成。

## 非目标与后续风险

- 本次不会从真实需求字段读取内容，也不会调用 Coding 服务。
- 历史不会跨刷新、跨设备或跨节点执行保存；如后续需要持久化，应由后端返回稳定的轮次 ID 和记录列表。
- Mock 流程通常不会自然触发异常分支，异常行为主要由纯函数测试和现有错误 UI 约束保证。
