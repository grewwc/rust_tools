## P1：Coding 网络异常可能重复启动远端 Run

- **状态：** 2026-11-11 已确认；按本轮决策先记录风险，不修改 Coding 恢复逻辑。
- **位置：** [`_run_initial_coding`](../src/conciliator/services/aeolus_service.py)、`_run_feedback` 的异常重试，以及 [`_send_tracked`](../src/conciliator/integrations/coco/aeolus.py) 的发送后游标保存。
- **触发条件：** 请求已被 Coco 接收，或 Run 已启动并保存游标，但响应/后续结果读取出现网络异常。进程在发送成功而游标尚未持久化的窗口退出，也存在发送结果不明的情况。
- **当前行为：** 初次和反馈 Coding 捕获 `TransientError` 后可能直接创建新 Session/Run，未先确认原 Run 已终止。发送后保存游标也不能完整区分“未发送”与“发送成功但未记录”。
- **影响：** 两个 Agent 可能同时修改、提交和推送同一任务分支；数据库租约只约束本地任务处理，不会停止已经启动的远端 Run。任务最终可能仍显示待确认，无法据此排除重复执行。
- **复现证据：** 使用本地 Fake runner，在首次 Run 游标保存后注入读取 `TransientError`；服务启动第二次执行，记录 2 个 attempt，最终状态为 `review`。未访问真实 Coco 或修改业务仓库。
- **运行注意：** 遇到发送/读取结果不明或服务重启，不要仅凭本地失败状态反复点击重试。维护者需核对原 Session/Run、分支 HEAD 和在途执行，确认后再决定恢复或替换；这些人工检查不能修复自动重试窗口。
- **待修复方向：** 持久化发送意图和结果不明状态；已有游标优先恢复原 Run；仅在确认原 Run 终止且可安全替换后创建新执行。对无法确认的发送结果保留待对账状态，禁止自动重复派发。
- **修复验收：** 覆盖远端已接收但响应丢失、结果读取超时、发送成功后进程退出，以及多进程接管；同一业务请求最多保留一个未确认终止的远端 Run，不能通过自动新建 Session 绕过。

## 多进程生产运行约定

生产启动脚本默认 `WORKER_NUM=4`，要求至少 2 个 Uvicorn worker；`MAX_REQUESTS` 默认 10000，达到上限后由父进程补充 worker。
不要在 TCE 保留 `WORKER_NUM=1`，该值会被启动脚本拒绝。实例数与进程数是两项配置，`WORKER_CONCURRENCY` 是每个进程的业务任务并发参数。

每个进程初始化自己的飞书长连接和后台 worker。发布前需验证共享数据库租约/去重在跨进程投递、worker 回收和重启恢复时的行为；连接池和业务并发需按进程数核算。多进程配置不会消除上面的远端重复 Run 风险。
